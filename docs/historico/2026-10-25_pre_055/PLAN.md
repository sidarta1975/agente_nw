15. **`sqlite3.Connection.backup()` recebe outra `Connection`, não um caminho de arquivo.** Para copiar para `dados/backups/agente_AAAA-MM-DD.db`, abra o destino com `conexao.abrir()` e passe essa conexão para `backup()` — nunca um caminho direto.
16. **`sqlite_vec` 0.1.9 aceita `INTEGER PRIMARY KEY` declarado em `vec0`** (testado na criação da migração 001); não foi preciso o fallback por `rowid` implícito previsto no brief 002.
17. **No `/api/generate` do Ollama, `think`, `format` e `stream` vão soltos no corpo; `num_ctx` e `temperature` vão dentro de `options`.** Confirmado contra o servidor real no brief 003. Todo prompt futuro (`qualificar`, `cruzar`, `extrair_de_texto`, etc.) passa por `ClienteOllama.gerar_json`, que já monta o corpo certo — nenhum módulo de produto deve montar essa chamada à mão.
18. **Testes que chamam o Ollama real nunca devem usar `config.container.banco()`** (aponta pro banco de desenvolvimento/produção real). Abrir uma conexão isolada com `conexao.abrir(tmp_path/...)` + `migracoes.aplicar()` e passar essa conexão direto pro `ClienteOllama`, sem passar por `container.llm()`.
19. **Contar comprimento de linha manualmente (sem rodar `ruff`) com `awk`/`wc -c` conta bytes, não caracteres — acento e travessão inflam o número.** Usar `len()` do Python (ou olhar direto), nunca ferramenta de shell orientada a byte, para decidir se uma linha passa dos 110 caracteres.
20. **`curl` sem `--compressed` mostra lixo binário em feed RSS servido com gzip** (ex.: `g1.globo.com/dynamo/...`), parecendo feed quebrado quando não está. `httpx` (usado de verdade pelo `leitor.py`) descomprime sozinho — testar candidato a fonte com `httpx` + `feedparser`, não com `curl` cru, para não descartar fonte boa por engano.
21. **`think: false` explícito no corpo do `/api/generate` está certo — não tirar o campo.** Testado direto contra Ollama 0.34.1 + qwen3:4b: sem `format: "json"`, omitir `think` dá resposta limpa e `think: false` faz o modelo "pensar" mesmo assim, jogando o raciocínio dentro de `response`. Mas **com `format: "json"` — que é como o projeto sempre chama** — o quadro se inverte: `think: false` é o único que dá resposta limpa; omitir o campo ou mandar `think: true` faz o JSON (às vezes até correto) parar dentro do campo `thinking` em vez de `response`, e `ClienteOllama` só lê `response`. Não testar essa configuração isolada de `format: json` de novo — o comportamento muda por completo com ele presente.
22. **HTTP 500 `"prediction aborted, token repeat limit reached"` do Ollama é falha de tentativa, não de rede.** Acontece quando o modelo entra num loop de repetição durante a geração (o Ollama aborta sozinho, é o guarda dele). `ClienteOllama.gerar_json` trata isso desde a correção pós-brief-003 igual a JSON inválido — nova tentativa, depois `fila_revisao` — em vez de deixar a exceção subir e derrubar o chamador (como continua acontecendo, de propósito, para falha de rede de verdade — servidor fora do ar, timeout de conexão).
23. **Memória do Ollama compartilhada com outros processos pode ser fator, mas não é a causa mais provável de JSON malformado.** Durante o brief 004, `ollama ps` mostrou `gemma2:9b` (6,6 GB) carregado ao lado do `qwen3:4b`, fora do controle da sessão — mas a correção que resolveu a instabilidade de verdade foi de prompt (armadilha 24), não de memória: 8/8 chamadas passaram a funcionar mesmo com o `gemma2:9b` ainda carregado. Checar `ollama ps` é diagnóstico útil, mas não parar a investigação nele.
24. **O exemplo resolvido de um prompt não pode ter o mesmo nome, cidade ou cargo do texto real que ele vai processar — o modelo copia conteúdo do exemplo, não só o formato.** Achado no brief 004: o prompt de `extrair_de_texto` tinha "Ricardo, diretor comercial, logística, Santos" como exemplo, e o texto de calibração do próprio brief usava exatamente os mesmos quatro atributos — o modelo devolvia a tag "cabotagem" (do exemplo) mesmo quando o texto real não mencionava cabotagem, com um `trecho` inventado que não existia na entrada. Sintoma parecido de outro jeito: exemplo com só uma tag no array não ensina o modelo a fechar um objeto e abrir o próximo — a segunda tag saía com chave errada ou o JSON truncava. **Todo prompt com exemplo resolvido** (`qualificar`, `cruzar`, `rotular`, `cartao` — briefs 008 e 009) **deve usar um cenário claramente distinto de qualquer entrada real prevista, e demonstrar pelo menos dois itens em todo campo que for lista.** Verificado com 8 chamadas reais consecutivas contra o Ollama antes e depois da correção (0/8 → 8/8 sem alucinação).
25. **`CNContactNoteKey` no `Contacts` framework do macOS exige entitlement de app assinado — um script Python do Terminal nunca vai conseguir ler nota, em nenhuma máquina.** Não é uma falha de permissão pontual nem algo que peça de novo; é política do sistema. Por isso `agenda_macos.ler_contatos()` busca a nota numa chamada separada (`unifiedContactWithIdentifier_keysToFetch_error_`) por contato, isolada em `try/except`, nunca dentro do `CNContactFetchRequest` principal — colocar `CNContactNoteKey` na chave principal do fetch faz a leitura inteira falhar (nome, telefone, tudo), não só a nota.
26. **API do PyObjC para `Contacts`: métodos Objective-C com `NSError **` viram, do lado Python, uma chamada que devolve `(valor, erro)` — não uma exceção.** `store.enumerateContactsWithFetchRequest_error_usingBlock_(pedido, None, bloco)` devolve `(sucesso, erro)`; `store.unifiedContactWithIdentifier_keysToFetch_error_(id, chaves, None)` devolve `(contato_ou_none, erro)`. Verificado contra a agenda real (547 contatos) no brief 005 — sem essa checagem de tupla, o código passa silenciosamente sem checar `erro`.
27. **Um upsert de `perfil_tema` que reseta `confirmado` a cada chamada desfaz confirmação do usuário se rodado de novo sobre o mesmo vínculo.** `perfil_tema.vincular()` é um `ON CONFLICT DO UPDATE` completo (inclui `confirmado = excluded.confirmado`), por desenho — é o que faz `agente_nw importar-temas` idempotente. Mas isso significa que qualquer código que chama `vincular()` de novo sobre um vínculo que o usuário já confirmou via `confirmar-tags` apaga essa confirmação. `agente_nw/perfil/importador.py` verifica `confirmado` antes de vincular um marcador e pula os que já estão confirmados — todo código futuro que reimporta/revincula tags existentes (briefs futuros que tocarem `perfil_tema`) precisa do mesmo cuidado.
28. **Testes que gravam em `vetor_item`/`vetor_assunto`/`vetor_tema`/`vetor_perfil` (tabelas `vec0`) precisam de vetores com exatamente 1024 posições — um vetor fabricado menor (ex.: `[0.1, 0.2]`) derruba com `sqlite3.OperationalError: Dimension mismatch`.** Completar com zeros até 1024 preserva o cosseno exatamente (dot product e norma não mudam com zeros extras nas mesmas posições dos dois vetores comparados) — é o padrão usado em `tests/test_agrupador.py`/`test_calibracao.py`/`test_itens_agrupamento.py`/`test_assuntos.py` (brief 007). Achado do mesmo jeito: `item.assunto_id`/`assunto_contato.assunto_id` etc. têm `FOREIGN KEY` de verdade e `conexao.abrir()` liga `PRAGMA foreign_keys=ON` — um teste que vincula um item a um `assunto_id` inventado (não gravado antes) derruba com `IntegrityError: FOREIGN KEY constraint failed`; sempre criar a linha real primeiro.
29. **`list[tuple[str, Literal[...], ...]]` não é aceito onde a assinatura pede `list[tuple[str, str, ...]]` — mypy estrito recusa por invariância de `list`, mesmo `Literal[...]` sendo subtipo de `str`.** Achado no brief 009: `cruzamento.py` montava `assuntos_para_prompt` a partir de `avaliacao.tipo` (`TipoConector`, um `Literal`) e passava pra `cruzar_por_que.construir_prompt(assuntos: list[tuple[str, str, str | None]])` — mypy recusou (`list` é invariante; `Sequence` seria covariante, mas as funções de prompt deste projeto tipam como `list` mesmo). Corrigido anotando o tipo explícito na criação da lista (`assuntos_para_prompt: list[tuple[str, str, str | None]] = [...]`), forçando o widening no ponto de construção em vez de deixar o mypy inferir o tipo mais específico. Vale para qualquer lista construída a partir de um campo `Literal` que precise entrar numa função tipada com `str` puro.
30. **Uma única `sqlite3.Connection` aberta na inicialização de um servidor Flask e reaproveitada por todas as rotas quebra com `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`, mesmo com `app.run(threaded=False)` (o padrão).** Achado de verdade no brief 010 (console web): o servidor de desenvolvimento do Werkzeug pode atender a primeira requisição numa thread diferente da que rodou `criar_app`. Todo o resto do projeto (CLI, `ciclo`, testes) abre uma conexão e usa do início ao fim na mesma thread — só um servidor HTTP de verdade expõe esse problema. Correção: cada requisição abre sua própria conexão sob demanda via `flask.g` (memoizada por requisição, fechada em `teardown_appcontext`) — não um `threaded=False` explícito (que já era o padrão e não evitou o erro) nem `check_same_thread=False` em `conexao.abrir()` (mudaria uma função usada em todo o resto do projeto para consertar um problema que só existe no console). Ver `agente_nw/console/app.py` (`_conn`/`_cliente_llm`) para o padrão de referência caso outro brief futuro suba outro servidor HTTP sobre SQLite.
31. **Teste que fixa uma data literal (`"2026-09-19"`) para representar "hoje" quebra sozinho quando o relógio vira o dia, se o código sob teste usa `datetime.now(UTC).date()` de verdade para decidir o que é "hoje".** Achado no brief 010: `tests/test_console_menu.py` gravava `assunto_contato.gerado_em` com uma string fixa; as rotas `/menu` do console filtram pelo dia real. `scripts/verificar.sh` rodou num dia diferente do que o teste foi escrito, e os três testes que dependiam de "hoje" falharam sem nenhuma mudança de código real ter acontecido no meio — só a data do relógio. Corrigido calculando a constante de "hoje" do teste com `datetime.now(UTC).date().isoformat()`, igual ao código de produção, nunca uma string escrita à mão. Vale para qualquer teste futuro que semeie linha comparada contra "hoje"/"agora" do sistema.
